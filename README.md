# 交易对账差错处置 Agent

一个交易资金对账系统（**业务世界做满、后端工程做薄**），上面跑一个**差错取证与处置 Agent**：
跨表取证 → 差错归因 → 生成处置方案 → 高风险动作走审批 → 执行后复核金额不变量。

项目的核心资产不是 agent 本身，而是 **可复现的带答案任务集 + 自动判分器 + 纯规则基线** ——
用来回答一个大多数 agent 项目回答不了的问题：**agent 到底比规则强在哪、弱在哪、贵多少。**

当前进度见 [STATUS.md](STATUS.md)。**阶段 0（业务世界层）、阶段 1（评测 + 规则基线）、阶段 2（Agent v1）已完成。**

## 30 秒上手

```bash
make build      # 一条命令：生成业务世界 + 账单 + 注入 20 类差错 + 对账 + 贴答案 + 校验不变量
make test       # 68 个测试，含答案质量守卫与设计性质断言
make report     # 差错池统计写入 docs/stage0_report.md
make baseline   # 跑纯规则基线并判分，写 docs/stage1_baseline.md
make agent      # 跑 Agent 并与规则基线同表对比（需要 .env 里的 DEEPSEEK_API_KEY）
make replay     # 回放一条判错的 agent 轨迹，逐步看它想了什么、调了什么
make case-composite   # 看一条复合差错的完整证据面
```

Python 环境固定为 conda `agent`。阶段 0 **没有引入任何新依赖**（见 [requirements.txt](requirements.txt)）。

## 它现在能产出什么

`make build` 默认参数（600 笔订单 / 3 天）下：

| | |
|---|---|
| 带答案的差错 | **500** 条 |
| 复合差错（≥2 个原因） | **95** 条 |
| 差错类型覆盖 | **22 / 22** |
| 无答案差错 | 0 |
| 白注入（注了但没产出差错） | 0 |
| 同 seed 可复现 | 逐字节一致 |

## ⭐ 核心结论：agent 和规则各自的位置

`make agent` 让两者跑**同一批 60 条任务**（模型 `deepseek-v4-flash`）：

| 指标 | 纯规则基线 | agent |
|---|---:|---:|
| 归因 exact（整体） | **76.7%** | 55.0% |
| 复合差错 exact | **100.0%** | 27.8% |
| **判据在结构化数据里**（n=46） | **100.0%** | 43.5% |
| **判据只在自由文本里**（n=14） | **0.0%** | **92.9%** |
| 错误动账（有害错误） | 7 条 | **1 条** |
| 越权处置 / 过度转人工 | **0 / 0** | 1 / 17 |
| 平均决策轮数 | 1.0 | 8.0 |
| 平均 token | 0 | 26.7k |
| 平均延迟 | 0 | 44 s |

> **agent 做到了规则结构上做不到的事（0% → 92.9%），
> 但在规则本来就满分的地方明显更差（100% → 43.5%）、更慢、更贵。**

所以结论不是「agent 更强」，而是**该按差错是否需要读自由文本来路由**。
这个项目一开始就是为了回答这个问题，现在有数字了，而且答案对两边都不客气。

### 缺陷诊断：差错边界越界

`make replay --failed-only` 回放的第一条就是典型：某条差错答案是 `["D10"] ["ESCALATE"]`，
agent 报了 `["D10","D14","D18"]` 并加上 `REVERSAL`。D14/D18 对那个订单也许确实成立，
但它们属于**别的差错记录**。agent 把同一订单上看到的所有问题都并进了这一条。

这一个缺陷同时解释了三个坏指标：复合 27.8%、过度转人工 17 条、越权 1 条。
阶段 3 的第一个靶子就是它。

## ⭐ 阶段 1 的核心结论：规则的上限在哪

`make baseline` 跑纯规则基线（零 token、零成本）：

| | 纯规则基线 |
|---|---:|
| 归因 exact（全部 500 条） | 88.8% |
| **判据在结构化数据里**（n=444） | **100.0%** |
| **判据只在自由文本里**（n=56） | **0.0%** |
| 其中「错误动账」（有害错误） | **30 条** |
| 误核销 / 越权处置 / 漏转人工 | 0 / 0 / 0 |
| 提示注入抵抗率 | 100%（结构性免疫，它不读 memo） |

这两行就是整个项目的立项理由：**规则引擎在能机械判定的地方已经打满 100%，
agent 唯一的立足点是那 56 条需要读懂自由文本的任务。**

### 这个结论是被逼出来的

第一次跑基线是**全项 100%**。原因很直接：我先设计注入器和 SOP、再照着 SOP 写基线，
于是每类差错都有一条机械可查的判据 —— 整个世界对确定性规则完全可解。
那样的任务集上「agent 比规则强」根本无从证明，后面所有阶段都是自娱自乐。

于是补了**自由文本证据层**：`channel_notices`（渠道公告，纯中文自由文本，
**故意不设任何结构化标签**），以及两个判据只存在于文本里的类型：

| 结构化证据 | 无覆盖性公告 | 有覆盖性公告 |
|---|---|---|
| 我方单边、渠道明细缺失 | **D01** → 发查询工单 | **D21** → 挂起等补发 |
| 手续费维度差异 | **D05** → 冲正记账（**动账**） | **D22** → 等渠道更正（**不动账**） |

两组的结构化证据**完全相同**。公告里还混了 5 种「看起来相关但不改变任何处置」的
干扰公告（维护通知、后台升级、风控调整、节假日安排、接口下线），
所以「当天有公告就挂起」这种偷懒策略拿不到分。

D22 的价值在于它让规则**主动做出有害动作** —— 去冲正一笔公告已明确要求不要动的账。
「安全地答错」和「有害地答错」价值完全不同，报表分开统计。

诚实的另一面：**规则引擎对提示注入结构性免疫**（100%），因为它压根不读 memo；
代价是它也**从不发现注入企图**（D19 召回 0%）。两面都写进结论，不粉饰。

## 为什么业务是真的

差错不是随机噪声，是**规则差异的必然产物**。四个渠道每一条规则都不一样：

| 渠道 | 手续费 | 舍入 | 日切 | 账单口径 | 结算 | 退款 | 币种 |
|---|---|---|---|---|---|---|---|
| 支付宝 | 0.60% | 四舍五入 | 00:00 | gross | T+1 | 原路退 | CNY |
| 微信 | 0.60% | 四舍五入 | **23:30** | **net** | T+1 | 原路退 | CNY |
| 银联 | 阶梯 0.5/0.45/0.38% | **银行家舍入** | **02:00** | gross | T+3 | 原路退 | CNY |
| PayPal | 3.4% + 2 元 | 四舍五入 | **08:00** | **net** | 周结 | **退到余额** | **USD** |

于是就有了这种**必须多步取证才能判完**的差错：

```
渠道账单某笔 998.00，我方记 1000.00，差 2.00

1  查订单     -> 原单 1000，状态「部分退款」
2  查退款     -> 有一笔 200 退款，发起于 T 日 23:47
3  查日切规则 -> 该渠道日切 23:30，这笔退款应落 T+1 账单，不该在 T 日口径里
4  但差额是 2 元不是 200 元 -> 退款不是差额来源，还有别的原因
5  查手续费   -> 费率核算恰好 2.00；该渠道账单是「扣费后净额」口径
6  查政策库   -> 口径差异属非差错，容差内自动核销
7  但第 3 步那笔退款的跨日归属是真差错 -> 挂起等 T+1 账单

结论：一条记录里套了两个问题 —— 一个自动核销、一个挂起
```

到第 4 步才知道「差额和退款无关」，这个判断依赖第 3 步的真实查询结果。
**规则引擎在这里塌掉，这就是 agent 不可替代的地方。**

## 正确性怎么证明

金额系统的正确性只能靠不变量证明，不能靠「看起来对」。

| 码 | 不变量 | 要求 |
|---|---|---|
| INV1 | 单笔守恒 | 订单与支付/退款自洽；累计退款不超原额 |
| INV2 | 全量守恒 | 我方合计 − 渠道合计（归一 gross）**恒等于**差错池残留，精确到分 |
| INV3 | 幂等 | 同一 idempotency_key 的资金动作执行次数 ≤ 1 |
| INV4 | 借贷平衡 | 每张凭证 Σ借 = Σ贷 |

INV1 被 D10 有意违反（注入生效的证据）；其余三条必须恒成立，不成立就是 bug。

## 答案质量守卫（最重要的一个设计）

`tests/test_ground_truth_quality.py` 检查的不是「代码有没有跑」，而是**答案对不对**：
对每一条标成 X 类的差错，验证 SOP 里 X 的识别依据在 **agent 可见的数据上真的成立**。

它在阶段 0 里抓出 4 个错标（另有 4 个真 bug，见 STATUS.md）：

1. **D03 落在支付宝上** —— 支付宝和我方同为四舍五入，「舍入模式不同」的识别依据不成立，
   正确答案其实是 D20。这类任务是**不可解的**。
2. **`Channel.rounding` 与 `FeeRule.rounding` 两处声明不一致** —— 银联只在 FeeRule 里设了
   银行家舍入，导致「银行家舍入渠道」集合为空，D03 一条都注不出来。改成派生属性。
3. **串号（D17）的受害方被标成 D17** —— 从可见证据看它和「渠道账单缺失该笔」完全无法区分，
   正确答案是 D01。
4. **D14 移位后仍落在同一账单日** —— 两侧照旧对得上，什么差错也没产生，只留一条白注入。

这些 bug 都不会让程序崩，只会让后面几周的所有指标变成垃圾，而且你会误以为是 agent 不行、
去调一周 prompt。**判分器和任务集是唯一不能赶的一步。**

## 目录

```
recon/
  money.py          金额（整数分）、四类手续费规则、两种舍入、口径归一
  config.py         4 个差异化渠道 + 5 个商户合约 + 容差分档 + 审批阈值
  schema.sql        14 张表；答案表与 agent 可见表物理隔离
  db.py             sqlite3 连接；AGENT_VISIBLE_TABLES / GROUND_TRUTH_TABLES
  world/
    generator.py    可复现交易流水（订单/支付/退款/分账/分录/结算）
    bill.py         按各渠道口径与日切生成 T+1 对账文件
    injector.py     ⭐ 20 类差错注入器，注入即标注，含复合差错与提示注入
  matching.py       对账匹配（只匹配不归因）+ 业务规则扫描 + 结算合规扫描
  invariants.py     4 条金额不变量校验器
  policies/         ⭐ 6 份政策文档，agent 必须检索，与生成器规则严格一致
  cli.py            命令行
tests/              48 个测试，含答案质量守卫与答案隔离守卫
```

差错池有**三个检测来源**，不只靠流水匹配：

- `match` 流水号匹配
- `rule_scan` 业务规则扫描 —— 如累计退款超原额，两侧记录一致，匹配根本发现不了
- `settlement_scan` 结算合规扫描

## Agent 的工程要点

```
recon/agent/
  llm.py      DeepSeek 客户端（OpenAI SDK + base_url，不为每家模型装一个 SDK）
              token/成本计量、空正文与坏 JSON 重试、FakeLLM 离线假模型
  tools.py    14 个只读工具，包在受控证据层外面 —— 和规则基线取同一份证据
              字段投影 + 行数预算；⭐4 个确定性计算工具，模型不做算术
  prompts.py  只给标签空间，不给识别依据（判据要它自己调 read_policy 去读）
  loop.py     harness：步数/成本上限、无进展检测、幻觉工具名回灌、
              结论词表校验、兜底一律转人工
  solver.py   线程池并发（每线程独立 sqlite 连接），轨迹主线程单写
```

harness 的价值不在「能调通模型」，而在**模型不听话时它还能给出安全的答案**。
`tests/test_agent.py` 25 个测试全部离线，逐一钉住：幻觉工具名、非法 JSON、
瞎编差错码、绕圈不收敛、轮数用完 —— 每一种的兜底方向都必须是「转人工」，
不能是「自动关闭差错」。

## 下一步（阶段 3）

按缺陷证据排序做消融，每项一行数字，对照组是 agent v1：

1. **明确差错边界** —— 治 scope creep，预期同时改善复合/过度转人工/越权
2. **把 diff_sop 提到 system prompt** —— 它被调了 55/60 次、每次 7KB，
   是 23.4k 输入 token 的主要来源；「会不会主动读政策」这个问题已经答完了
3. **维度清单式收敛** —— 复合漏报形态很一致（`D01,D05→D01`），都是「找到一个解释就停」
4. 降低主动放弃率（17 条 UNKNOWN 全是模型主动放弃，0 条来自基础设施）
5. 时间线折叠 + 证据引用（原计划的 context 工程）
