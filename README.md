# 交易对账差错处置系统 —— 规则优先路由 + 受限语义复核

一个交易资金对账系统（业务世界做满、后端工程做薄），上面跑差错取证与处置。

**项目最核心的结论不是准确率，是一个架构判断：**

> **开放式多轮 agent 在闭合业务问题上既贵又不稳定。**
> 把确定性逻辑交给规则、把模型压缩成受限的自由文本复核器，
> 效果和稳定性都会显著改善。

这个结论是被自己的测量逼出来的，不是先想好的 —— 中间推翻过四次自己的判断。
完整过程见 [STATUS.md](STATUS.md)。

当前进度：**阶段 0~5.6 已完成；阶段 6.1 holdout 已封存、尚未正式评测；
阶段 6.2 配对统计工具已完成、真实重复运行样本未齐**，210 个测试。

## 30 秒上手

```bash
cp .env.example .env          # 任选 OpenAI-compatible / OpenAI / DeepSeek / Ollama / vLLM
python -m recon.cli llm-config # 只看最终解析结果；不联网、不泄露完整密钥
pip install -r requirements.txt
make build                    # 造世界：1400 订单 / 1192 条带答案的差错
make test                     # 210 个测试（agent 侧全部离线，不联网）
make route-dry                # 只跑闸门，看要花多少钱（零模型调用）
make route                    # 核心交付物：规则优先路由 + 单次复核
```

其它：`make baseline`（纯规则）、`make agent`（全量 agent 对照）、
`make variance`（方差与 pass^k）、`make ablate`（消融阶梯）、
`make replay`（回放一条判错的轨迹）、`make repro`（验证可复现）、
`make archive-stats`（累计攒了多少轨迹）、`make archive-export`（导出 SFT 用 JSONL）、
`make holdout-build`（只构建并封存，不调模型）、`make holdout-check`（核验封存状态）。

### 模型配置

推荐只填三个通用变量：

```bash
RECON_LLM_MODEL=你的模型名
RECON_LLM_BASE_URL=https://你的兼容端点/v1
RECON_LLM_API_KEY=你的密钥
```

配置解析顺序固定为：命令参数 → `RECON_LLM_*` → `OPENAI_*` →
旧 `DEEPSEEK_*` → 本地 `OLLAMA_*` / `VLLM_*`。已有 DeepSeek `.env`
无需迁移；本地端点无需伪造真实密钥。

不同兼容接口的能力差异也会自动处理：不支持 `response_format` 时退回提示词约束
和严格 JSON 解析；不支持 `max_tokens` 时改用 `max_completion_tokens`；
不支持 `temperature` 时省略该参数。自动选择只根据本地配置，**不会偷偷探网或试模型**。

## 一、这套东西是什么

```
       生成交易与账单 → 注入 22 类差错 → 同时写下答案
                          ↓
        受控证据层（白名单 / 轨迹 / 返回值预算 / as_of 时间切片）
                          ↓
                   规则基线先跑（零成本）
                          ↓
            结论可能被当日公告推翻？──否──→ 直接采用
                          │是
                          ↓
        读当日公告 → 单次 LLM 复核 → 维持 或 D01→D21 / D05→D22
                          ↓
      自动判分 → 风险 / 成本 / 稳定性 / 场景覆盖 四张报表
```

每跑一次，轨迹都会追加到一个**独立的、只追加的归档库**（`data/archive.db`）：
原样发出去的 messages、模型原样返回的 response、答案、判分、溯源。
世界库怎么重建都不影响它。

规模：开发世界 1192 条任务；独立 holdout 1185 条任务 / 31 条公告；
210 个测试，19 张业务表 + 归档 2 张，6 份政策文档。

## 二、核心结果（1192 条全量，独立跑 2 次完全一致）

| 指标 | 规则基线 | 全量多轮 agent | **规则优先路由 + 复核** |
|---|---:|---:|---:|
| 归因 exact | 91.9% | 52~60% | **100.0%** |
| **判据只在自由文本里** | **0.0%** | 71~93% | **100.0%** |
| 判据在结构化数据里 | **100.0%** | ~50% | 100.0% |
| 终态正确 | 97.0% | 68~74% | **100.0%** |
| **错误动账（有害错误）** | **36 条** | 0 | **0 条** |
| 平均决策轮数 | 1.0 | 7~8 | **1.2** |
| 平均未缓存输入 token | 0 | 4400+ | **23** |
| 平均延迟 | 0 | 40~46 s | **约 1 s** |
| 需读文本 exact 三次极差 | — | ±7.1pp | **±0pp** |

闸门本身零成本：路由 **336/1192 = 28.2%**，需读文本召回 **97/97 = 100%**，
放行的 856 条规则本来就全对。

### ⚠️ 关于这个 100%，必须说清楚

**它不能当最终结论。** 当前世界只有 25 条公告、每类语义 1~2 个模板，
1192 条任务里很多共享同一条公告和同一种判断逻辑。

> **1192 是业务记录的样本量，不是自由文本语义的有效独立样本量。**

这个 100% 能证明的是：**路由架构在当前生成世界里是闭合的**。
阶段 6.1 已把独立 holdout 封存：新措辞，以及跨午夜窗口、金额区间限定、
多公告叠加、部分撤回、公告与内部政策冲突。当前状态仍是 `sealed`，
**没有运行模型、没有 holdout 分数**。正式结果只允许产生一次，避免
「看结果 → 调 prompt → 重跑」演变成对 benchmark 的手工过拟合。

## 三、四次被数据推翻的自己的判断

这部分比任何准确率数字都重要。

**① 第一版规则基线全项 100% —— 那是红灯不是成绩。**
我先设计注入器和 SOP、再照着 SOP 写基线，整个世界对确定性规则完全可解。
那样「agent 比规则强」根本无从证明。→ 补出自由文本证据层（渠道公告 + D21/D22）。

**② 不量方差就读消融表是无效的。**
同配置 `temperature=0` 跑出 92.9% / 85.7% / 78.6% / 64.3%，极差 28 个百分点，
而消融各级差异只有 5~14 点。**我差点把噪声当成结论去追。**
→ 先量噪声下限，再把每个改动除以该指标自己的噪声，只有 ≥3 倍才算信号。

**③ pass^1 会系统性高估可用程度。**
全量 agent pass¹ 52.2%，**pass³ 只有 21.7%**，翻转率 58.3%。
→ 主要问题是稳定性不是准确率，而稳定性的根源是多轮累积。

**④ 「设计了但没生成出来」是静默失败。**
加难点后两个最难场景实际只有 1 条和 0 条样本 —— 不报错、不变红，
只在报表上多一行 100%。→ 新增场景分档 + 样本量守卫。

## 四、三条反复出现的设计原则

### ① 模型不做算术，交给确定性代码

工具层里手续费核算、口径归一、容差查档、账单日归属、时间差全是确定性工具。

阶段 5 直接验证了它的价值：模型在语义判断上全对（整天覆盖 100%、
主题近似但明确不覆盖 100%、后续更正收窄 100%），但
**「这个时刻是否落在 09:00-12:00 之间」只有 33%**。
加一块由代码算好的归属表 → **100%**。

> 模型读得懂「是什么」，做不好「精确比较」。

### ② 答案与求解方在接口层强制隔离

答案存在独立的表，受控证据层运行时拦截，基线代码静态检查不许出现答案表名，
复核器提示词校验不含答案解释片段。

**措辞要准：这是接口层强制隔离，不是数据库级物理隔离** ——
同一个 SQLite、同一个连接，只是求解方拿不到绕过 `EvidenceView` 的路径。

### ③ 判分器和任务集是唯一不能赶的一步

`tests/test_ground_truth_quality.py` 是最大的测试文件。它检查的不是
「代码有没有跑」，而是**「答案对不对」**：对每条标成 X 类的差错，
验证 SOP 里 X 的识别依据在 **求解方可见的数据上真的成立**。

它抓出的错标，每一个都不会让程序崩，只会让后面几周的指标全变成垃圾：

- D03 落在四舍五入渠道（那里「舍入模式不同」不成立）
- D04 落在 gross 口径渠道（清零手续费字段不产生任何可见差异）
- D05 落在有费率公告的日子（可见证据支持 D22）
- 串号的受害方被标成 D17（从证据看无法与 D01 区分）

**三次都是复合路径绕过了原子路径的守卫，而测试也三次只查了原子。**

## 五、安全语义：三个曾经存在的 P0

这三条会直接推翻「零错误动账」和「fail-safe」这两个结论，都已修复并有测试守住。

**P0-1 复核失败时保留规则结论 —— 在动账场景下不安全。**
原实现 `except LLMError: return prior`，注释还写着「这是安全方向」。
但 D05 的 prior 就是 `REVERSAL`。真实答案若是 D22（公告已说明渠道会自行更正、
明确要求商户不要动账），**一次 API 超时就会执行掉这个项目最想避免的错误动账**。
→ 含动账动作时剥离动账、转人工；只读动作原样保留。
另外 `LLMFatalError` 继承自 `LLMError`，复核器原来没单独处理 ——
402 欠费会让全批静默退化成规则结论。→ 必须穿透中止。

**P0-2 typed 分类闸门的 fail-safe 实际上不 fail-safe。**
分类失败原来回落到 `delay`，注释写「一律当覆盖性」。但 delay 只对 D01 是覆盖性，
对 D05 不是；而闸门按类型分集合查。于是**一条费率公告分类失败 → D05 查不到 →
不进复核 → 规则直接 REVERSAL = 错误动账**。
→ 新增 `unknown_covering` 标签，同时进 delay 与 fee 两个集合。
宁可多路由（白花钱），不能漏路由（动错账）。

**P0-3 时间穿越式证据泄漏。**
对账任务原定在账单日次日 07:00，而公告 09:30 才发布，且公告查询不看
`published_at` —— 求解方读到了两个半小时后才存在的信息。
→ `Task.as_of` 时间切片 + 按 `published_at` 过滤；更正公告发布时间改为 10:30
（真的晚于原公告）；对账时刻改到 11:00（真实对账是在渠道当日公告发布之后才跑的）。
两个方向都有守卫：不能读到未来公告，也不能因为卡太早导致覆盖性公告全看不见。

## 六点五、轨迹归档：跑一次留一次

原来的轨迹是**一条都没剩**的，三处叠加：`persist_runs` 每次先 DELETE、
`make build` 整库 `reset=True`、复核结果压根没落库（而它最适合做 SFT）。
再加上 `make clean` 是 `rm -rf data`。实测 `agent_runs: 0 行` ——
阶段 2~5 烧掉的 token 产生的所有轨迹全没了。

**这是个不报错的错**：程序正常退出、报表正常打印，只有回头找数据时才发现空的。

现在是独立一层（`recon/archive.py` → `data/archive.db`），四条硬规则：
只追加、跨世界重建存活、存够能重建训练样本的东西、溯源齐全（世界指纹 +
`git rev` + 模型 + 配置）。

**答案和输入分两组字段存，永不拼接。** 守这条的测试值得一说 ——
最初写的「答案字符串不许出现在 messages 里」是**错的**：复核器合法地看得到
规则先验，`D01`/`D05` 本来就在提示词里，先验又常常正好等于答案，必然误报。
真正的不变量是：把 task 上的答案字段抹掉，提示词应当一个字节都不变。

首次归档 336 条，其中最值钱的是 **2 条失败样本** —— 模型看到延迟公告
就想把手续费差异（D05）也归到 D21，而延迟公告只覆盖 D01。这是真实语义错误，
被校验拦下、动账动作被剥离、转人工。**一次会错误动账的判断变成了过度转人工。**
所以这一跑动作 exact 是 99.8% 而不是 100% —— fail-safe 生效，不是回归。
