# 训练闭环：设计、理由，以及为什么现在不做

> **状态：明确不实现。** 本文只记录思考，不落代码。
> 决策时间 2026-07-27。决策人：项目所有者。
> 理由：前期工作量已经很大，训练是独立的一条腿，现阶段投入产出比不合适。

这份文档存在的意义是：**把"为什么没做"和"如果做该怎么做"写清楚**，
而不是在计划里挂一个永远排在最后的"阶段 7：可选 SFT"。
之前那样挂了四个阶段，一次没兑现 —— 挂着不做比明确不做更糟，
因为它让人误以为这条腿还在路线图上。

---

## 一、为什么这件事被反复提起

它对应两类不同的岗位需求：

| 岗位 | 现在这个项目 | 缺不缺训练 |
|---|---|---|
| AI 应用开发 / 后端 | 完全够，甚至偏强 | 不缺 |
| **业务大模型算法** | 会被读成"很扎实的工程项目" | **缺一条腿** |

项目所有者在最早的讨论里就说过这件事：

> "agent 是可以当作投业务大模型算法的项目，但是业务大模型那种是要你重新看点
> 这个内容然后做类似 minimind 的那种工作"

这个判断是对的。业务大模型算法岗看的是**模型效果闭环**（数据构造 → 训练 →
评测 → 错误分析 → 再迭代），而本项目目前止于"用现成模型 + 好架构"。

---

## 二、如果做，为什么这个项目是最好的起点

绝大多数人做 SFT 卡在两件事上，而这两件在这里都已经有了：

```
1192 条带答案的任务          <- 注入即标注，零标注成本
自动判分器                   <- 归因/处置/风险/成本，七类场景分档
336 条模型实际处置过的轨迹     <- agent_runs / agent_steps 全量落库
纯规则基线                   <- 可以回答"训练到底值不值"
```

也就是说：**训练所需的数据和评价体系是现成的**，缺的只是训练那一步本身。

---

## 三、如果做，最值钱的问题是什么

不是"能不能微调出一个模型"，而是这个：

> **规则优先路由已经把问题压缩到：一次调用、输入 942 token、
> 输出空间只有三个选项（维持 / D01→D21 / D05→D22）。
> 那还需要 flash 这个量级的模型吗？一个 1.5B 微调过的够不够？**

两种结果都是结论，而且都值钱：

- **够** → 成本降一个数量级，而且这正是国内业务团队最想听的话（降本）
- **不够** → 说明"读懂中文公告的语义"这件事本身有能力门槛，架构再好也压不掉

注意这个问题只有在**架构先做对了**之后才问得出来。如果还是全量多轮 agent，
输入 27k token、8 轮、输出空间开放，小模型根本没有可比性 —— 那时候问
"小模型够不够"是没有意义的。

**先架构、后训练**这个顺序不是偷懒，是必要条件。

## 四、如果做，具体怎么做

### 4.1 数据从哪来

不是重新造，是从已有轨迹里挖：

| 来源 | 数量级 | 用途 |
|---|---|---|
`agent_runs` / `agent_steps` | 336 条复核轨迹 | 正样本（判对的） |
判分器标出的 bad case | 见报表 | 负样本 / 难例 |
七类难点场景 | 各 7~43 条 | 分层，保证每类都有 |
"证据不足应转人工"的任务 | UNKNOWN 那批 | 拒答样本 —— 缺了会训出过度自信 |

关键：**必须包含拒答样本**。只喂"判对了的"会训出一个从不说"我不确定"的模型，
而在这个业务里过度自信的代价是错误动账。

### 4.2 划分

按**公告模板**划分，不是按任务随机划分。同一条公告下的任务共享判断逻辑，
随机划分会让训练集和测试集里出现同一条公告 —— 那是泄漏，测出来的分数是假的。

这一点和 `docs` 里 holdout 的设计是同一个原则。

### 4.3 训练

- Qwen2.5-1.5B-Instruct 起步，7B 作对照
- peft + trl 做 LoRA，不做全参
- GPU：AutoDL 4090 约 2 元/小时，跑完几十块

### 4.4 评测

**直接复用现成的判分器和场景分档**，不另造评价标准。要出的表：

| | flash（现状） | 1.5B 原始 | 1.5B + LoRA |
|---|---|---|---|
七类难点场景各自 exact | | | |
错误动账 条数 | | | |
未缓存输入 token | | | |
单任务成本 | | | |
pass^3 | | | |

以及消融：只训语义判断 / 只训拒答 / 两者都训。

## 五、为什么现在不做（诚实版）

1. **它是一条独立的腿，不是这条腿的延伸。** 前面五个阶段的产出（世界、判分器、
   基线、路由、复核器）互相咬合；训练是另起一摊，需要 GPU 环境、数据管线、
   训练调试，和现有代码几乎不共享基础设施。
2. **现在有更紧的事。** 外部 review 找出三个 P0 安全语义 bug，它们会直接推翻
   报表上"零错误动账"和"fail-safe"这两个结论。带着已知的安全 bug 去做训练，
   等于在错的基线上叠新东西。
3. **泛化可信度还没解决。** 当前 100% 是在 25 条公告 / 每类 1~2 个模板的世界上跑出来的。
   在这个基础上训练，训出来的东西同样只对这些模板有效。**先做 holdout，再谈训练。**

---

## 六、什么条件下应该重新捡起来

按优先级，满足下面任一条就该重新评估：

1. **投递反馈显示卡在"缺模型效果闭环"** —— 简历过不了业务算法岗的筛，
   或者面试被追问"你有没有做过训练/数据构造"
2. **holdout 建完并且路由在未见模板上仍然稳** —— 那时候"小模型够不够"这个问题
   才有干净的实验床
3. **有现成 GPU 且时间宽裕** —— 边际成本低到不值得再权衡

在那之前，这条腿的替代讲法是（诚实且成立的）：

> "这个项目里我没有做训练。我先回答了一个更前置的问题：这个业务里模型到底该
> 用在哪、用多少。答案是只有 28% 的差错需要模型，而且只需要一次调用、942 token。
> 在把问题压缩到这个程度之前，讨论用什么模型、要不要微调都是过早的。"

这个讲法的好处是它**不掩盖缺口**，而是说明缺口是主动排序的结果。
面试官如果追问"那你会怎么做训练"，本文第四节就是答案。

## 附：不要做的几种做法

- ❌ 从零搓 MiniMind 再改注意力/层数 —— 那只证明跑通了训练代码，
  不证明能做业务效果闭环
- ❌ 拿现成公开数据集微调 —— 和这个项目脱节，等于两个不相干的项目拼在一起
- ❌ 只报"微调后 loss 降了 / 几个对话截图" —— 没有基线、没有分场景、没有成本对比，
  说明不了任何事
