# 阶段 4：规则优先路由 —— 闸门设计与取舍

## 出发点：阶段 3 的负面结论

消融表读出来的结论是负面的：三个 prompt 靶子累积只值 1.7 个点，而且噪声下限
本身就有 7 个点（见 `variance`），也就是说这些差异读不出信号。继续调 prompt
是在噪声里捞针。

但同一批数据里有一组互补得非常干净的数字（全量 505 条，`cover_k=4` 那版世界）：

| | 条数 | 规则基线 exact | agent exact |
|---|---:|---:|---:|
| 判据在结构化数据里 | 446 | **100.0%** | ~50% |
| 判据只在自由文本里（D21/D22） | 59 | **0.0%** | 85.7% |
| 整体 | 505 | 88.8% | 58.3% |

> 本文所有数字来自 `cover_k=4` 的世界。世界重建后条数会变，但结论的形状不会 ——
> 用下面那条命令随时复算，别信这里的绝对值。

两边完全互补。所以下一步不是「把 agent 调得更聪明」，而是**让规则先跑，只把
它注定读不到的那部分交给 agent**。

## 闸门依据来自公开 SOP，不是答案

`policies/diff_sop.md`「必须查阅渠道公告」一节：

| 结构化证据 | 无覆盖性公告 | 有覆盖性公告 |
|---|---|---|
| 我方单边、渠道明细缺失 | **D01** → CHANNEL_INQUIRY | **D21** → HOLD_NEXT_BILL |
| 手续费维度差异 | **D05** → REVERSAL（**动账**） | **D22** → HOLD_NEXT_BILL（不动账） |

只有 D01 / D05 两个结论的结构化证据与「有公告」情形完全相同。规则给出其它结论
（D09/D03/D20/…）时公告改写不了它 —— 那条差错没有付 agent 的必要。

## 候选闸门的实测对比

全量 505 条，零 token（`python -m recon.cli route --all-tasks --dry-run` 复现闸门 2 那行）。
agent 侧按实测分组准确率折算：需读文本 85.7%、规则可解 50.0%。

| 闸门 | 路由比例 | 需读文本召回 | 放行部分正确率 | 现实预期 exact |
|---|---:|---:|---:|---:|
| 0 全部交给 agent（阶段 3 那条路） | 100% | 100% | — | 54.2% |
| 1 当日有任何公告就路由 | 63.0% | 100% | 100% | 72.7% |
| **2 有公告 且 结论含 D01/D05** | **21.8%** | **100%** | **100%** | **93.3%** |
| 3 公告分类完美（无结构条件，不可实现） | 56.4% | 100% | 100% | 76.0% |
| 4 = 2 + 3 | 13.5% | 100% | 100% | 97.4% |

**闸门 2 是不需要任何模型就能实现的那个**，也是当前采用的方案。

两个值得记下来的读数：

1. **结构前置条件的贡献远大于「能不能读懂公告」。** 只加结构条件（闸门 2）
   到 93.3%，只做完美公告分类（闸门 3）只有 76.0%。先做便宜的那个。
2. **规则的 UNKNOWN 信号完全无用**：全量上规则一次 UNKNOWN 都没输出过（0/505），
   在它答错的 59 条上召回是 0。「让规则自己说不知道」这个直觉设计在这里是死的
   —— 它是自信地答错，不是老实地弃权。这也是为什么闸门必须建在
   「结论形态 + 证据是否存在」上，而不是建在求解方的置信度上。

## 闸门只决定「谁来答」，不决定答案

这个不对称是整个设计成立的原因：

- **漏放**（该路由却放行）→ 规则必错。D22 判成 D05 会去冲正一笔本不该动的账，
  是有实际资金损失的错误。
- **误触**（不该路由却路由）→ 只是白花 token。

所以闸门按**召回优先**设计，宁可多路由。`tests/test_router.py` 把
「需读文本召回 = 100%」钉成断言，而不是「足够高」。

## inner 用复核，不用重解

被路由的 110 条里有 51 条是误触 —— 规则本来全对，交给 agent 从零重做反而可能
做坏（agent 在规则可解题上只有 ~50%）。所以 inner 不该是「重解方」。

`recon/agent/reviewer.py` 是**单次调用**的复核器：拿规则的结论当先验，只回答
「当日公告是否推翻它」。两个设计要点：

1. **不是 agent 循环，是一次调用。** 闸门已经把「要不要读公告」判完了，剩下的
   证据是闭合的（公告全文 + SOP 的 D21/D22 一节），没有「取了才知道下一步取
   什么」的探索需求。路径确定，就不该让模型来决定路径。
2. **输出空间被结构性限制**成「维持」或「D01→D21 / D05→D22」，它造不出新归因。
   这正是那 51 条误触的保护：最坏也只是被错误挂起，不会变成任意错误结论。

### 结果（全量 505 条，deepseek-v4-flash）

| 指标 | 规则基线 | **router-review** | 阶段 3 全 agent |
|---|---:|---:|---:|
| 归因 exact | 88.3% | **98.6%** | 58.3% |
| ⭐需读文本 exact | 0.0% | **100%** | 85.7% |
| ⭐**错误动账 条/元** | 39 / 62.97 | **0 / 0.00** | — |
| 终态正确 | 92.3% | 100% | 66.7% |
| 复合 exact | 100% | 92.3% | 33.3% |
| 规则可解 exact | 100% | 98.4% | 50.0% |
| 平均决策轮数 | 1.0 | **1.2** | 8.2 |
| 平均 token | 0 | **283** | 27,762 |
| 平均延迟 ms | 0 | **1,094** | 42,071 |

token 差 98 倍、延迟差 38 倍，准确率还高 40 个点。

**稳定性**：同配置连跑两次 —— 归因 98.8% / 98.6%，需读文本 100% / 100%，
错误动账 0 / 0。对比阶段 3 多轮 agent 在同一指标上 64.3~92.9% 的摆动：
砍掉轮数直接砍掉了不稳定的来源，这正好打在 pass^3 那个结论上。

## 一次失败的提示词实验（记下来，别再试）

剩余缺陷是**误改判**：改判 65 条，而真正的 D21/D22 只有 59 条。定位到 9 条陷阱，
形态一致 —— 复合差错 `D09,D05` / `D14,D05`，当日确实有费率误用公告，但那个
D05 是真的 D05。

而且这两者**在证据上完全可分**：规则给 D22 陷阱写的依据以「渠道手续费…」开头，
给真 D05 写的以「我方手续费…」开头，505 条上零例外。公告原文说的也正是
「商户侧记账正确、错在渠道侧」—— 这是个前提条件，改判前本就该核对。

于是在提示词里加了这段前提核对。结果**净负**：

| | 加之前 | 加之后 |
|---|---:|---:|
| 规则可解 exact | 98.7% | 99.3% ↑ |
| 复合 exact | 93.4% | 96.7% ↑ |
| ⭐需读文本 exact | **100%** | 88.1% ↓ |
| ⭐错误动账 条/元 | **0 / 0.00** | 7 / 7.34 ↓ |

它在针对的那个问题上确实见效，但把模型整体推保守了：误改判少了，**却多漏 7 条
真 D22，又开始冲正不该动的账**。按 SOP 的代价不对称（漏判有资金损失，误判只是
延迟一天），这是往坏方向换。已回退。

**教训：代价不对称的任务上，提高精确率的措辞很容易以召回为代价，而那个代价不
出现在总准确率里。** 只盯 exact 会得出「99.3% > 98.7%，改对了」的错误结论。

### 1. 结构化手续费事实（针对剩余误改判）

上一节那次失败实验的教训是「要更好的**证据呈现**，不是更严的措辞」。所以这次
只加证据、措辞一个字不改 —— 这是个干净的对照实验。

规则在算手续费维度时把三方对照记进 `Solution.facts["fee"]`（我方 / 合同费率
复算 / 渠道，以及偏离的是哪一侧），复核器把它渲染成一张表放进提示词。

依据是实测：规则给 D22 陷阱写的 notes 以「渠道手续费…」开头，给真 D05 写的以
「我方手续费…」开头，505 条零例外。信息本来就在，只是埋在中文自由文本里。

### 2. typed 闸门：公告分类一次，全局复用

公告全库 13 条、差错 505 条。`recon/agent/notice_classifier.py` 给每条公告打一次
标签（`delay` / `fee` / `none`），落盘缓存，闸门只在**类型对得上**时才路由。
调用次数与任务数无关 —— 这是这一层存在的全部理由。

**但这一层把安全性质改坏了，必须写清楚：**

| | any 闸门 | typed 闸门 |
|---|---|---|
| 误判方向 | 多路由 = 白花钱 | **漏标覆盖性公告 = 漏放 = 错误动账** |
| 召回依赖 | 无（按构造 100%） | 分类器质量 |

所以分类器按 fail-safe 设计：拿不准归为覆盖性；调用失败、标签无法解析 ——
一律当作覆盖性。`tests/test_notice_classifier.py` 里有一条测试专门毒化一条覆盖性
公告的标签，断言它**确实会造成漏放** —— 记录风险，而不是假装没有。

## 一个 fail-safe 差点骗过我的教训

第一次跑分类器，13 条公告全部返回 `delay`，统计出来「危险方向漏标 0 条」，
看起来完全正常。实际是账户欠费、13 次调用**全部失败**，全被 fail-safe 兜成了
覆盖性标签。不是拿标题 oracle 对了一遍，根本看不出来。

而且这些兜底标签当时**会被写进缓存**，那就是永久污染 —— 之后每次跑都命中缓存，
连「没分类成功」这件事都看不见了。

修法有三条，都已落地：

1. `classify_one` 多返回一个 `ok` 布尔值，把「真结果」和「兜底」分开；
2. **兜底结果绝不入缓存**；
3. `label_stats` 单独报 `fallbacks` / `trustworthy`，CLI 在有兜底时打红字警告
   「本次数字不可用于下结论」。

教训比这个 bug 本身值钱：**fail-safe 让系统在故障时继续产出，代价是故障看起来
像正常结果。** 凡是有兜底分支的地方，都必须有一个计数器把兜底次数暴露出来，
否则你迟早会拿一份全是兜底的数据去下结论。
